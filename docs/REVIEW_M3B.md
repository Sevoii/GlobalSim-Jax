# M3b preliminary review criteria — deterministic lateral mechanics

**Scope:** source-backed lateral primitives and supplied-target lane movement only, layered on accepted M3a. Reference is the pinned Rust tree at `58da7bc4693d9aa8f6340e348cba1c5b5fb5a856`; relevant routines are `retail_sort::comparison_sort`, `retail_lane::{resolve_overlaps, side_room, is_visible, MoveState::step}`, and `overtaking::is_target_with_block_check`. This is criteria for later implementation review, not an implementation acceptance.

## Required source behavior

- **Comparison sort:** port the actual comparison introsort permutation, including median-of-three pivoting, insertion sort for partitions of size at most 16, heap fallback, and swaps of equal keys. Stable sort or a generic library sort is not equivalent. Include a duplicate-key case larger than 16 that reaches the partition path and compare the exact index order to an independently compiled Rust oracle.
- **Overlap ordering and mutation:** sort runner indices by `(lane as i32)` (truncation toward zero, including negative fractional lanes), using the source comparison sort so equal integer keys preserve its exact permutation. Set only the first sorted runner’s force-check flag false; when an adjacent pair satisfies both strict tests `abs(position delta) < 0.4` and `abs(lane delta) < f32(0.4_f64/18)`, set the current runner lane to the already-mutated previous lane plus that f32 step and set only its force flag true. This is a chained adjacent pass, not a simultaneous pairwise projection. Do not clamp the correction to lane rails. Cover exact threshold edges, equal/truncated keys, a three-runner chain, preexisting force flags, and out-of-rail results.
- **Side room and visibility inputs:** side-room starts from rail distances/permissions, scans the supplied roster order, ignores peers at `abs(position delta) >= side_distance`, and treats same-lane peers as neither side. Inner/outer gaps update minimum available room; blocking uses strict `< side_lane`, with the inner blocker/index overwritten by each qualifying encountered inner peer. Visibility is forward-only: `0 <= gap <= vision`, with `vision > 0`; cone width preserves the source f32/f64 operation sequence and inclusive lane-width edge. Freeze boundary and next-f32 cases.
- **Overtaking eligibility:** preserve f64-to-f32 narrowing before comparisons. Reject `gap < -1`; a direct blocker is eligible exactly when its f32 speed is less than owner target. Otherwise require inclusive gap `[1,20]`, positive speed gap, and `gap/speed_gap <= 15`; then choose between peer current speed and target speed comparisons according to the shared pre-movement blocker query. Test inclusive/exclusive edges, NaN behavior where accepted by the source API, and that irrelevant cases do not perform the deferred blocker scan.
- **MoveState update order:** first clamp target to `[0,max_lane]`; approximately-equal target clears continuation time and returns before direction or speed updates. Otherwise save old direction and update direction before speed work. Normal movement computes the mixed f32/f64 rate, rank/outer factor, acceleration and modifier clamp in source order; speed persists even if the later side-permission check blocks displacement. Near-zero modified speed returns before lane/timer mutation. Displacement uses widened `lane + dt*speed`, clamps toward target, then clamps rails, then tests side permission. On blocked movement, preserve the already-updated target/direction/speed but do not advance continuation time or lane. On accepted movement, advance continuation time only if direction matches its prior value; zero speed when approximately at target. Freeze exact bits for f32 state and relevant f64 temporaries in both eager and JIT.
- **After-goal branch:** when the caller supplies `after_goal`, use signed `dt` as lateral speed (thus displacement contains `dt` twice); omit normal acceleration, modifiers and inward-lane multiplier. Still preserve common target clamp, directional target clamp, rail clamp, side-permission rejection and movement/timer state ordering. Test inward/outward and blocked post-goal vectors. This standalone branch does not mean M3a’s integrated first-finish freeze should be removed or claim full retail post-goal scheduling.
- **Integration observation points:** supplied targets may feed `MoveState`, but field/row snapshots and live rows must remain distinct where the source caches pre-movement visibility/side permissions and samples live corridor/peer values later. Apply overlap resolution as its separate manager pass after all runner moves, in the source order; do not fold it into each lane update or apply it simultaneously. Keep lane/target/move/force state per runner and independent across batch lanes.

## Acceptance evidence

Use independently compiled Rust original modules or a small copied-source Rust oracle, with revision/provenance recorded; expected values must not be generated by the JAX implementation. Freeze vectors for every ordering/boundary case above, including exact sort permutations and chained overlap outputs. Compare every state/output bit against Rust in eager and JIT paths, and run true `[2,2]` batch cases against scalar per-race/per-runner execution. Include an order-sensitive multi-runner integration case proving the overlap manager pass sees all movement results and mutates the same force flags as Rust. Keep fixture hashes and verify pinned source hashes before fixture regeneration.

## Explicit exclusions and claims

This slice accepts only **supplied target** movement and deterministic helpers. AutomaticTargetState/passing-target generation, target collection, RNG-driven outward targeting, pacing (`AutomaticTargetState` and pacing portion), lane preference/strategy decisions, and any unported skill/callback effects remain unsupported and must be unavailable or explicitly rejected; do not replace them with invented target or pacing equations. Preserve M3a’s accepted bounded contract. M3b/M3c as a whole, complete race parity, post-goal race scheduling, GPU correctness, and GPU speedups remain unaccepted absent separate source-backed implementation and evidence.

## Bounded snapshot review: standalone MoveState unit (2026-11-16)

Reviewed `globalsim_jax/lane_move.py`, its current `tests/test_lane_move.py` draft, and the already-inspected Rust `retail_lane::MoveState::step`. No tests were run while the draft is being edited. This is not an M3b acceptance.

1. **Checked wrapper accepts scalar leaves it does not canonicalize:** `step_checked` accepts Python integer `context.rank`, `context.phase`, and `context.modifier_count`, and Python booleans for `after_goal`/side permissions (`lane_move.py:156-166`), then passes the original dataclasses directly to `step`. `context.rank` is used via `.astype` (`107`), which fails for Python `int`; `~context.after_goal` and `~context.can_in/out` (`123,127`) apply Python integer inversion for bools. Normalize every validated pytree leaf into the declared JAX scalar/vector dtype before calling the kernel, or reject scalar Python/NumPy forms not supported by the kernel. Add checked-wrapper tests using precisely the accepted scalar forms, including Python `rank` and permission booleans. `_apply_modifiers` explicitly converts the modifier vector to JAX f32 before tracer indexing (`82`), so I found no separate NumPy-modifier indexing defect in this snapshot.
2. **Zero-speed early return is ordered after inward scaling:** Rust checks approximately-zero immediately after modifier application and `[0,0.6]` clamp, before applying the inward lane multiplier (`retail_lane.rs:700-710`). The JAX kernel applies the multiplier to `adjusted` first (`119`) and checks `speed` afterward (`123`). For ordinary magnitudes the predicate is effectively unchanged, but a subnormal adjusted speed can cross the absolute comparison floor when multiplied by `(1+lane)`. Carry the source zero-return decision from the adjusted pre-inward value and verify bit-exact subnormal inward cases.
3. **Current tests do not cover full state on early/blocked paths:** `test_copied_rust_move_vectors_eager_and_jit` asserts only lane, target, speed, and `moved` (`test_lane_move.py:31-41`); its fixture setup seeds continuation time/direction as zero (`19`). Add frozen whole-state cases for a blocked move retaining updated momentum/direction but not lane/time, blocked direction reversal preserving timer, successful direction reversal, and blocked/inward/outward after-goal movement. Assert lane, target, speed, continuation time, continuation direction, and moved in eager and JIT; exercise checked host inputs separately.

The normal-path calculation inspected here otherwise follows the source's mixed-precision rate/acceleration, modifier fold, target/rail clamps, side check, and timer update placement. Recheck this first unit after Terra fixes the checked boundary and adds full-state edge vectors; automatic targets, pacing, field integration, and the remainder of M3b are outside this snapshot.

## Bounded design review: supplied-target integration over M3a (2026-11-16)

Read-only source review of `race_field_retail::step_all_retail` (`src/race_field_retail.rs:182-342`), `race_solver_retail::step_forward_retail_with_roster` (`src/race_solver_retail.rs:969-1320`), and the current M3a `field.step`. No tests were run and no implementation was changed.

1. **Keep two different field observations.** Retail lane collection caches `side_room`/`can_in`/`can_out` from the tick-entry roster before `prepare_retail_tick` and skill-priority passes (`race_field_retail.rs:190-232`). After those passes and `flush_skill_effects`, the manager rebuilds live rows and samples front blocker/gap and blocking timers before stepping runners (`234-275`). For the supplied-target, no-skills M3a profile these may share the same positions, but preserve the API distinction: freeze the side-permission snapshot for the entire tick; do not recompute it after an earlier runner moves. The M3a post-preparation front/gap snapshot remains the source for blocker identity and cap.
2. **Interleave lateral movement with each ordered longitudinal step.** The manager advances indices in supplied order; inside one runner's solver step, pending HP/minimum and start gate are handled first, then lane target/movement state is processed, and only later are longitudinal acceleration/distance and position updated (`race_solver_retail.rs:1000-1031,1176-1186,1208-1276`). In the restricted M3a integration, compute that runner's lane context from its current pre-longitudinal position/rank, apply the supplied target with the frozen side permissions, then advance that same runner longitudinally before visiting the next index. Do not move all lanes simultaneously or run every lateral update after the longitudinal loop; either changes the position/context observation point and later-runner visibility of prior state.
3. **Respect the gate early return and partial-tick distinction.** A fully closed gate updates minimum and delay before returning without reaching `MoveState` (`race_solver_retail.rs:1028-1031`); therefore no lane, target, speed, direction, or continuation-time change occurs on that lane while its gate remains closed. When the gate opens partway through the tick, source still calls lateral `MoveState.step` with full `dt`, while the longitudinal distance is multiplied by `gate_fraction` (`1275-1276`). Keep this extracted behavior explicit and cover both a closed-gate return and a fractional gate-opening trace. M3a's own prevalidated clock/minimum updates remain subject to its accepted policy.
4. **Run overlap once, after all per-runner movement.** `resolve_overlaps_with_order` is called after the solver loop and consumes rows rebuilt from post-longitudinal positions plus the lanes produced by lateral movement (`race_field_retail.rs:300-323`). It updates lane and `force_check` in that separate manager pass; do not resolve after each runner or use pre-longitudinal positions. Preserve the first-unit sort permutation, strict chained correction, and no rail clamp. Carry force flags as state if they affect later supplied-target ticks; otherwise explicitly limit the adapter to one-tick outputs.
5. **Preserve M3a's terminal boundary without claiming retail post-goal integration.** M3a permits the crossing tick, must complete its active runners' supplied-target and longitudinal work plus the post-movement overlap pass, then marks the batch truncated and freezes every state leaf on subsequent scan rows. Skip all movement/overlap mutation for a batch already truncated, including lane target/speed/direction/timers and force flags. A standalone `MoveState` may test the Rust `after_goal` branch, but integrated M3a's checked runner does not accept a live post-goal batch; do not use that helper to imply M3a continues finished runners, applies retail post-goal longitudinal deceleration, or reproduces full `step_all_retail` scheduling.
6. **Oracle the adapter as an extracted subset.** Since compiling the full Rust manager currently hits unrelated `TargetState` borrow errors, use an independently compiled copied-source `MoveState::step` plus a small source-order adapter for the restricted manager schedule. Record exactly which source functions/order are extracted; serialize per-tick pre-side snapshot, per-runner pre-longitudinal context, lane state, longitudinal state, gate fraction, post-pass overlap lane/flags, and terminal/truncation fields. Compare all those fields bitwise in eager/JIT and independent `[2,2]` batch-vs-scalar tests. The copied-source adapter establishes only this restricted schedule, not complete engine trace parity.

This integration criteria remains narrower than automatic target generation, pacing, skills/callbacks, and full field scheduling; those are not implied by the design or by M3a acceptance.
