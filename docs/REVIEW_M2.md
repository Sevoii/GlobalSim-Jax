## Feasibility and scope decision

A fixed-shape, flat-course, no-skills loop over independent runners is feasible as an explicitly restricted subset. The runner dimension must not imply cross-runner field behavior: no roster reads, ranks/ties, blockers, pacing, lane movement, overtaking, rushing/competition, duel effects, or peer skills. The loop may be flat-only while the milestone separately adds source-backed stat adjustment and fixture-backed geometry-table primitives, as required by `PORT_PLAN.md` and the coordinator's direction. These primitive APIs need not be integrated into flat-loop movement.

The current `docs/MILESTONE_2.md` draft conflicts with that scope by excluding stat adjustment and all captured geometry. Amend its inventory before calling the plan ready: include a bounded, explicit stat-adjustment inventory and a bounded, fixture-backed geometry-table inventory, while keeping loop integration flat-only. Geometry should name exactly which `CourseGeometry` operations are supported; do not label a partial table lookup as complete course geometry.

## Reference findings and acceptance criteria

### Inputs, stat adjustment, and initialization boundary

- Reference `src/retail_initialization.rs:9-12` defines `initial_base_wisdom`: clamp mood to [-2, 2], form the f32 coefficient `(10000 + 200*mood) as f32 * 0.0001_f32`, multiply f32 raw wisdom, then clamp [1, 2000]. The source has exact constructor vectors at `:19-30`. M2 must include this source-backed adjustment (or identify the intended equivalent stat adjustment explicitly) and test its operation order. Every additional conversion must map to a pinned Rust function/table and have independent expected values; do not derive new formulas from plausibility.
- Distinguish raw stats, initialized/adjusted stats, and runtime stats in the input schema. Validate finite values, valid strategy/aptitude codes, and documented ranges before tracing. The current draft's explicit numeric inputs are compatible with a restricted contract, but do not claim seed-to-race initialization parity: skill random-trigger scanning, wisdom checks, delay sampling, 24 section draws, and rushing draws in `retail_initialization.rs:87-253,480-513` are outside a caller-supplied-state loop unless ported in full source order.
- The official initialization fixture `retail_initialization_official.json` contains 10 source-hashed official cases, 90 runners, `expected_start_delays`, and `expected_rushing_sections`. Its source note says official practice exports; identifiers are omitted. Use only assertions supported by those fields. It is not a generic full-initializer oracle for arbitrary rosters or skill data.

### Geometry-table primitives

- Add a separate geometry module/API with an exact supported-function list from `src/retail_geometry.rs`. At minimum, each implemented table/query primitive must be compared against `retail_geometry_port.json`; that fixture has 119 course entries, captured-asset hashes, and per-row inputs (`position`, `lane`, `movement`, `previous_world`) plus expected f32 bit channels. Preserve the pinned fixture bytes/provenance and validate course identity; unknown or mismatched courses must error rather than substitute another table.
- The geometry fixture describes a v75 GlobalSim-engine regression snapshot with inputs from the reconstructed Python port, not universal game parity. Its row assertions support only the listed sampled geometry inputs/outputs. If position interpolation, quaternion correction, overrun, or movement correction is omitted, list it as unsupported. Geometry primitives can ship separately from movement; the flat loop must not silently consume them.

### Ordered movement, start gate, HP, and phase

- Match the order in `src/race_solver_retail.rs:995-1033,1157-1175,1206-1329` for the supported no-skills path. In particular, during start dash the minimum is 3.0 (unless the runner is already finished) and speed is capped by `Parameters.start_dash_speed`; do not use the ordinary guts-based minimum during that branch. The dash ends only at the source threshold (`actual >= dash_limit`) and applies the source acceleration adjustment.
- Gate semantics are not equivalent to multiplying the whole tick by the gate fraction. `advance_start_delay` returns no active movement for `dt == 0` and computes a crossing fraction for a gate crossing (`retail_physics.rs:109-120`). Retail movement first forms `actual * dt` and applies the fraction to displacement (`race_solver_retail.rs:1274-1277`); the special start-dash HP drain receives the full `dt` (`hp_policy.rs:279-285`, called at `race_solver_retail.rs:1290-1295`). Preserve these separate rules and test zero-time, below/equal/above countdown, and partial-gate crossings.
- Port the special gate HP drain separately from ordinary quadratic HP drain: `20 * rate * ground_modifier`, rounded to f32, then subtract `drain * dt` and clamp HP at zero (`hp_policy.rs:279-285`). Ordinary HP drain uses the M1 helper only after start dash and consumes the source state/current speed. Test phase/rate/ground combinations, HP exhaustion, and the exact switch tick. A single generic HP equation is not faithful.
- Preserve observation points. Retail computes the tick's speed and HP before updating phase from the solver's current (pre-position-advance) `self.pos`; position is assigned later (`race_solver_retail.rs:1278-1305,1306-1322`). Thus crossing a phase boundary during displacement does not retroactively change that tick's HP/acceleration. Add immediately-before, exact-boundary, and immediately-after traces.
- Implement no-skills acceleration, target clamp, start-dash cap, and minimum/maximum clamp in source order. If the restricted config disables automatically scheduled spurt or any non-skill state such as rushing, declare those as explicit input preconditions; “no skills” alone does not imply those systems are absent.

### Finish, stopping, and timeout semantics

- Distinguish the solver's crossing flag from the field's step mask. The retail solver marks `finished` only after new position is strictly greater than course distance (`race_solver_retail.rs:1317-1322`), while field drivers select runners whose pre-step position is strictly less than distance (for example `:274-277` and `:440-458`). An exact-equality runner is therefore not stepped on the next field tick even though the strict crossing flag may not have been set. Test exact equality separately from overshoot; do not collapse these states without documenting the reduced contract.
- Use adjacent-tick finish interpolation only on a real crossing with source-compatible previous/current positions and times. A timed-out lane must remain distinct from a finisher and must not receive an invented finish time or result rank.
- The Rust source examined here does not define the M2 `max_ticks` timeout as a retail race rule. It may be a bounded execution-safety cap, but label `timed_out` as wrapper/output truncation, define whether the cap includes the zero-time initialization step, and avoid presenting it as engine behavior.
- Stop stepping lanes consistently with the M2 contract. Retail field callers stop scheduling a runner at `pos >= distance`; an isolated solver can still be called post-goal and has post-goal state. M2 should match the field active-mask behavior for its loop, not claim that the standalone solver never advances after finish.

### Independent oracle and tests

- A copied-source Rust oracle is acceptable for the extracted subset if its source files, pinned commit, license/provenance, adapter changes, and build/run command are recorded. Generate expected tick rows from this Rust code independently of JAX; tests must load frozen rows and compare every supported per-tick channel. The oracle is evidence for the copied subset only, never full-engine or universal retail parity.
- Existing `retail_solver_port.json` (10 isolated traces, 26 bit/flag channels) and `retail_field_port.json` (5 whole-field traces, 26 channels per runner) are GlobalSim-engine v75 regression snapshots with reconstructed-Python inputs. Even an empty-skill isolated trace still exercises section/geometry/automatic-state behavior outside a flat, disabled-feature loop. Do not report their full-trace parity as M2 acceptance. They can help identify source channels and later milestones.
- `retail_hp_port.json` provides 20 × 500 sampled HP rows with velocity, phase, flags, heal, rate bits, and HP bits; it is a component regression snapshot, not a complete start-gate/runner tick oracle. Add restricted Rust-oracle cases specifically for gate drain and phase observation.
- Exact f32 bits are required for source f32 stores; use the established finish-time tolerance only where the fixture/source contract warrants it. Required tests: scalar-vs-batch independence, JIT execution, fixed-capacity and mask behavior, nontrivial multi-tick movement/HP, start-dash/gate edge cases, phase boundaries, exact-goal/overshoot, timeout-vs-finish, and geometry primitive boundary rows. Invalid unsupported inputs must fail clearly before an approximate path can run.

## Current draft risks

1. `docs/MILESTONE_2.md` omits stat adjustment and geometry table primitives despite the original M2 plan and current coordinator direction. Add them as separately tested APIs; keep flat-loop integration explicitly excluded.
2. The phrase “uses only M1-validated source functions” is incomplete for the loop: M1 does not cover start-dash minimum selection, special gate HP drain, or the interaction/order of these helpers with speed, phase, and finish state. Add these source-backed rules; do not invent replacements.
3. Supplied `start_delay` and numeric runner inputs deliberately bypass much of `initialize`; disclose that no seed/skill initialization parity is claimed. Likewise, any automatically occurring rushing/spurt behavior disabled by this subset must be an explicit restricted condition.
4. `max_ticks` is an execution cap, not a demonstrated retail timeout rule. Keep timed-out separate from finished and from finish-time interpolation.
5. The copied-source oracle protects against JAX implementation drift but does not independently validate the complete GlobalSim engine. Keep the oracle's exact extraction boundary and copied-source provenance visible in tests/docs.

M2 is not ready for implementation acceptance until the plan includes the directed stat-adjustment and geometry-table primitives, enumerates the source-faithful gate/HP/phase/stopping rules, and specifies a frozen copied-source Rust trace oracle for only the restricted subset. ## Historical `restricted.py` scaffold findings (superseded by final handoff review)

Snapshot reviewed after coordinator-requested scaffold feedback. These are implementation defects to fix before final review; no tests were run in this bounded pass.

1. **High - phase transitions are late and skip phase 1's first boundary** (`globalsim_jax/restricted.py:71`). The expression transitions at 16/24 and 20/24 only. The Rust boundary table is `[4/24, 16/24, 20/24, distance]` and phase is the count of crossed boundaries capped at 2. Use the existing `phase_boundaries(distance)` values and the source count/cap rule; add just-before/at/after checks for each threshold.
2. **Resolved - start-dash minimum selection** (`restricted.py:55-64`). The current snapshot selects the 3.0 minimum during dash and ordinary guts minimum afterward. The subsequent review below records that cap-then-floor is the observed Rust order; it is not itself a defect without evidence of a supported cap/minimum contradiction.
3. **High - HP drains before the gate opens** (`restricted.py:65`). The HP update is masked by `active` but not `gate`, so a runner with positive remaining delay loses HP on ticks where `advance_start_delay` returns no movement. Mask HP updates by `active & gate`; for the tick that crosses the gate, preserve the source's full-`dt` special dash drain rather than scaling that drain by the movement fraction.
4. **High - special dash drain omits ground modifier** (`restricted.py:61-65`). `dash_drain` is fixed at 20. The source gate formula is `20 * rate * ground_modifier` rounded to f32 before subtracting `drain * dt`; in this no-status subset `rate` can be 1, but the supplied ground modifier still applies. Include it and test non-unit ground.
5. **High - timeout is not sticky and inactive lanes keep changing state** (`restricted.py:42,65,69-73`). The returned `timed_out` is the newly computed `timeout`, so the next call clears it once `active` is false. `advance_start_delay` also changes delay for finished/timed-out lanes, and `new_phase`/`start_dash` are recomputed for them (and can change while the gate is closed). Preserve existing terminal flags with `state.timed_out | timeout`; freeze per-runner state for finished/timed-out lanes, and on a closed gate update only the countdown/time fields allowed by the contract.
6. **Moderate - shape/capacity and compiled input validation are not implemented** (`restricted.py:28-36,39`). The docstring says shapes must match, but construction does not check them or enforce a capacity/finite-value contract; only concrete strategies are checked, with the check bypassed for traced strategies. Add a host-validated entry point for shape, capacity, finite/range, strategy, distance, nonnegative `dt` (including the zero-time case), and positive `max_ticks`, or state explicit low-level JIT preconditions and validate before compilation. Do not let malformed arrays fail later from nested `vmap` with opaque errors.
7. **Moderate - there is no run/scan API yet** (`restricted.py:39-73`). `step` performs one tick; `max_ticks` only affects that tick, so callers cannot obtain the documented bounded run, timeout trace, or finish output through a package-level loop. Add a fixed-length `lax.scan`/run wrapper that records required per-tick state, stops updates through masks, and distinguishes wrapper timeout from finish.

The file currently has no explicit speed cap after the minimum floor (`restricted.py:53-56`); once the start-dash minimum is corrected, validate that supported inputs keep the post-floor speed within the source cap, or add the required final cap if the selected source contract requires it. Current review is limited to this file and does not assess geometry work.

## Bounded geometry snapshot review

Reviewed `globalsim_jax/geometry.py`, `tests/test_geometry.py`, `tools/geometry_oracle.rs`, and the packaged `course_10101.json`/package manifest only. No tests were run in this review.

### Actionable findings

1. **High - mixed-precision geometry does not check the x64 precondition** (`globalsim_jax/geometry.py:31-42,49-56,69`). The module constructs f64 sample coordinates and performs f64 interpolation/correction but never calls the package's `require_x64()` guard. With JAX x64 disabled, those requested f64 arrays/operations can be truncated, undermining exact geometry bits. Check x64 on `load`/public entry before building the arrays; raise without changing process-wide JAX config, and add a test for the disabled-config error.
2. **Moderate - host validation is bypassed or fails for mixed traced inputs** (`geometry.py:44-47,66-69`). `position` checks inputs only when both are non-tracers, so a concrete invalid distance/lane is unchecked when the other argument is traced. `advance` gates on `distance` but calls `float(movement)`, which fails for a traced movement paired with concrete distance; it also never validates that `previous_world` is a finite length-2 vector. Split host validation from the jitted kernel (or use a checked JAX path) and validate movement and previous-world data against their own inputs.
3. **Moderate - packaged asset identity and array schema are only partially verified** (`geometry.py:24-42`). The loader checks the requested id/distance and lengths of `x`, `z`, and `rotation`, but it does not compare the resource's embedded `course_id`/`course_identity` to the request or verify aligned `y` length, `(1001,4)` quaternion shape, rotation-fix shape, and finite table values before constructing JAX arrays. Validate these metadata/shapes so a malformed or mismatched package resource raises a clear error instead of producing plausible but incorrect coordinates.
4. **Moderate - direct Rust-oracle coverage is one hard-coded sample** (`tools/geometry_oracle.rs:9-14`). The oracle imports the pinned `retail_geometry.rs`, but runs only one input and does not record the source revision/hash in its own output. `test_geometry.py:16-24` compares all 315 in-course rows for course 10101 against the copied v75 engine snapshot in eager and JIT; that is useful regression coverage, but only the one hard-coded row currently has direct oracle confirmation. Extend the oracle to emit a documented boundary sample set (or all supported fixture inputs) and record the pinned source revision and output hash; keep claims limited to this course/subset.
5. **Moderate - segment-boundary behavior lacks explicit adjacent-float assertions** (`tests/test_geometry.py:26-32`). The all-row test covers every 315 in-course rows in the fixture, including three rows each at 0 and 1200 m; the endpoint test checks finiteness, not exact endpoint bits. Add explicit `nextafter` cases around sample-index boundaries and exact start/end expectations so interpolation-index rounding and the terminal raw-quaternion branch are pinned even if the snapshot row selection changes. The 24 overrun rows are excluded consistently with the module's stated unsupported overrun scope.

### Confirmed coverage and provenance

- The package contains only the explicitly supported `course_10101.json`; `pyproject.toml:23-24` includes it as package data. Its SHA256 is `ae75a726bd10e7270d8cb236e952bfce4c92bbb142e2eaffd5019ce8d4f183e1`, matching the course 10101 `captured_asset_sha256` recorded in `retail_geometry_port.json`. The resource carries course identity and source-asset hash fields.
- The current test iterates all 315 fixture rows with `0 <= position <= 1200`; eager comparisons check all four expected bit channels, while the JIT comparison checks next position and both world coordinates. `lane_max` is currently a course-wide scalar, not a per-position lane-width table. ## Restricted loop bounded follow-up (current snapshot)

Reviewed only `globalsim_jax/restricted.py`; no tests were run. This supersedes stale scaffold statuses above where the code now shows a correction.

- **Resolved in snapshot:** phase thresholds now come from `phase_boundaries(distance)` and count crossed boundaries capped at 2 (`restricted.py:80-81`); gate masks movement and HP drain (`65-74`); dash drain includes ground (`72-74`); timeout is sticky and per-runner state fields are masked for inactive lanes (`49,74,78-83`); a fixed-length `run`/`lax.scan` wrapper exists (`86-92`).
- **Not established as a defect - dash floor/cap ordering:** `restricted.py:62-64` applies the source-observed cap followed by the selected minimum floor. This matches the Rust ordering. Do not require reordering absent evidence that a supported input can make the cap lower than the active minimum; if that range is possible, capture a source-backed edge case before changing behavior.
- **Moderate - initialization validation can be bypassed by a traced strategy:** the finite/distance and strategy checks are all guarded only by `not isinstance(strategy, Tracer)` (`restricted.py:35-39`). If strategy is traced, invalid concrete distance or non-finite stats bypass host validation; if strategy is concrete while other inputs are traced, Python conversions of traced arrays can fail. Separate a host-validated API from the low-level JIT kernel and document traced-bound preconditions explicitly.
- **Moderate - `step`/`run` lack an input validation boundary:** `step` accepts `dt`, `max_ticks`, distance, and per-runner inputs without shape, finiteness, range, or nonnegative-time checks (`restricted.py:45-46,60,75-92`). `run` validates only `max_ticks > 0` (`88`), which is unsuitable when called with traced values and does not validate the arrays passed through `inputs`. Add/require validated host inputs before compilation; keep low-level dynamic bounds as documented caller preconditions.
- **Moderate - timeout semantics are tick-count only and the wrapper returns padded terminal rows:** `run` always scans exactly `max_ticks`, while `step` marks timeout when the incremented count reaches the limit (`78-80,86-92`). This is acceptable only as wrapper truncation; document the returned scan as fixed-length with terminal state repeated/frozen (except global `time`, which currently increments even when every lane is terminal at `83`) and do not describe it as retail timeout parity.

This follow-up is a snapshot, not final loop acceptance. The geometry review above remains separate; the next review should verify fixes and tests together.

## Historical restricted Rust oracle extraction review (superseded where noted below)

Reviewed only `tools/restricted_oracle.rs` against source-order and behavior facts already gathered; no new Rust-source exploration or tests were performed.

1. **High - finish predicate does not match the tick crossing contract** (`tools/restricted_oracle.rs:22-23`). It marks finished only when `s.pos > distance`; the recorded engine/restricted contract detects a crossing with previous position below the goal and new position `>= distance`. Exact-goal ticks therefore diverge, and the oracle has no previous-position guard. Record `previous` before movement and use the same crossing predicate as the extracted source; include exact-equal and overshoot cases.
2. **Moderate - speed and acceleration aptitude factors are conflated** (`restricted_oracle.rs:9,17,28-30`). `Acceleration.distance` is an aptitude coefficient, not course length; the Rust retail solver derives it from the distance-aptitude basis-point entry (6000/5000/4000 for the relevant grades, scaled by `0.0001f32`). The oracle currently supplies the same `aptitude` value used by `base_target_speed`, so it cannot represent differing speed- and distance-aptitude factors. Give the oracle separate inputs for both factors, or explicitly restrict and validate fixtures to cases where both are `1.0`; do not pass course meters into this field.
3. **Moderate - trace output omits state needed to audit the adapter** (`restricted_oracle.rs:30`). Rows emit time, position, speed, HP, phase, dash, and finished, but omit remaining delay and finish-time bits. The delayed case therefore cannot directly verify the gate countdown, and finish behavior cannot be compared exactly. Emit those state channels plus an explicit gate/fraction observation where available; pin expected output in frozen tests.
4. **Historical coverage gap - expanded in the current snapshot** (`restricted_oracle.rs:28-39`). This earlier oracle had three cases; the current fixture has six cases including exact-goal field stop, dash exit, and zero-HP deceleration. Coverage remains limited to those extracted branches and is not a complete engine trace.
5. **Moderate - provenance is not reproducible enough to freeze evidence** (`restricted_oracle.rs:1-4,27,29`). The comment says “pinned” but source paths point at a mutable checkout, the emitted provenance names only `retail_physics.rs`, and the parameter file is also read from an absolute working-tree path. Record the Rust commit or file hashes, parameter asset hash, extraction boundary, and oracle output hash alongside the fixture/test so future runs can establish which source produced the evidence.

The adapter does preserve the main observed order in its current body: delay/gate, target and acceleration using the incoming phase, speed update, HP drain using that phase, phase refresh, movement/finish, then dash-state refresh (`11-24`). Its arithmetic state fields are `f32`; movement alone widens the product before applying the f64 gate fraction (`22`). The evidence-backed oracle issues are the finish predicate and aptitude-factor conflation above. Treat this as an extracted-subset oracle only, not complete Rust engine parity.

## Intermediate bounded M2 implementation snapshot (superseded by final handoff decision)

At that earlier snapshot, `.venv/Scripts/python.exe -m pytest tests -p no:cacheprovider` passed **11 tests**, and `tests/test_restricted.py` was absent. That statement describes only the intermediate snapshot and is superseded by the final 17-test run below.

### Findings requiring correction before restricted-loop acceptance

1. **High - integer stamina truncates fractional course distance during initialization** (`globalsim_jax/restricted.py:83-85`). `stamina_a` preserves its input dtype, then `jnp.full_like(stamina_a, config.distance)` uses that dtype. With integer stamina and an accepted nonintegral distance, the value passed to `initial_hp` is truncated (for example, 1200.5 becomes 1200). Create the distance array explicitly as f32 (or use a f32 reference array), and cover integer-stat inputs with a fractional distance.
2. **High - checked runner entry does not enforce the required x64 precision** (`restricted.py:105-106,129,157-167`). The kernel widens movement arithmetic to f64, but `run_checked` has no `require_x64()` guard; with x64 disabled JAX can truncate these operations. Guard the checked API before execution without mutating global JAX configuration, and add a disabled-x64 error test. Direct `step`/`run` may remain documented low-level kernels with an explicit caller precondition.
3. **High - checked runner entry accepts malformed state values and dtypes** (`restricted.py:91-103,157-162`). `_validate_state_and_inputs` checks state shape only. NaN/inf in physical state, invalid phase/tick values, and non-bool terminal/dash flags can enter `run_checked` and either propagate or change control flow; only `finish_time` needs the documented NaN sentinel for unfinished lanes. Validate state dtypes and invariants, allowing that sentinel only where appropriate, before execution.
4. **Resolved after this snapshot - restricted regression coverage** (`tests/test_restricted.py:63-127`). The current suite consumes six frozen cases in eager/JIT and compares a divergent `[2,2]` batch against scalar eager/JIT traces.

### Resolved findings and bounded decision

- Geometry now calls `require_x64()` at load/position/advance (`geometry.py:34-36,67-70,91-93`), checks embedded identity and table dimensions/finiteness (`41-50`), and validates concrete inputs independently, including `previous_world` (`67-72,91-100`). The all-row course 10101 fixture test passes eager and JIT over all 315 in-course rows. The earlier geometry guard/schema/input-validation findings are resolved for the bundled course and current package asset.
- The restricted source-order corrections visible in this snapshot include phase-boundary counting, gate-masked HP drain, ground-adjusted dash drain, sticky terminal flags, and freezing terminal lane state (`127-146`). The cap-then-floor order is source-matching and is not reported as a defect. The prior oracle concerns about exact-goal crossing and separate speed/distance aptitude inputs remain applicable to `tools/restricted_oracle.rs` until its adapter and frozen tests are updated; this final pass did not re-open Rust source.

**Decision: accept the geometry primitive only for bundled course 10101 and its tested in-course fixture domain; do not accept the restricted runner yet.** The remaining initialization/precision/state-validation defects are code issues, and the restricted loop currently lacks executable frozen-trace and true batch tests.
