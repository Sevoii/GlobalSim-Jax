## Schedule corrections and required contract

The plan's main observation points match the extracted retail schedule, with these details made explicit for implementation and its oracle:

1. **Ranks are prior-pass state, not refreshed per runner.** `race_field.rs:205-225` copies the previous rank vector and recomputes order only when `RaceField::update()` is called after the field pass. `race_field_retail.rs:182-330` does not update rank inside the runner loop. Every `MoveContext.rank` in one tick must therefore use the same cached rank, even if an earlier runner crosses or changes position. Include a multi-tick crossing case that distinguishes cached rank from a recomputation during the current pass.

2. **Side cache has its own earlier snapshot and stable roster indexing.** `step_all_retail` first captures each runner's pre-movement `(position,lane)` and roster in solver-index order, then calls `lane.collect_roster` for each owner before per-runner preparation/skill passes (`race_field_retail.rs:190-219`). `TargetState::collect_roster` excludes the owner by concatenating indices before then after it (`retail_lane.rs:114-130`); blocker indices and last-inner-blocker selection consequently depend on that stable order. Keep this side/visibility/target cache distinct from the later front-blocker snapshot, which is sampled after the skill pass (`race_field_retail.rs:231-258`). With skills excluded, document that the side cache represents tick-entry rows; never rebuild it from earlier runners' moved lanes. Test an order-sensitive cached-side case and preserve original roster-to-peer index mapping.

3. **The closed-gate early return is later than minimum/delay updates but before lane movement.** `step_forward_retail_with_roster` updates minimum speed and advances/stores start delay before returning when `gate_fraction` is absent (`race_solver_retail.rs:1018-1032`). Thus a closed gate must skip `MoveState` target/speed/continuation/direction changes and longitudinal movement, but this does not imply the whole Rust runner state is unchanged. Keep M3a's previously accepted truncation mask separate: a truncated batch freezes all leaves on subsequent calls. Include an explicit closed-gate test with nontrivial lane continuation state.

4. **Movement is ordered, with a refreshed live roster after each runner.** In `race_field_retail.rs:276-299`, each runner completes `step_forward_retail_with_roster`; its updated horse is written back to `roster[i]` before the next runner. When a callback dirties the roster, the source refreshes it. The bounded no-skills profile may omit callback machinery, but it must preserve runner order and publish each prior runner's new position, lane, speed, and target before processing the next. Within the solver, `MoveState::step` precedes longitudinal speed/position/HP work; partial gate fraction scales longitudinal distance only, while lateral movement receives full `dt` (`race_solver_retail.rs:1176-1200,1270-1280`).

5. **Overlap uses final longitudinal positions and lanes, once after the runner pass.** The source rebuilds overlap rows from all solvers only after every indexed runner has advanced, calls `resolve_overlaps_with_order`, then stores corrected lanes and force flags (`race_field_retail.rs:303-329`). Do not use tick-entry or per-runner intermediate positions, skip gate-closed rows, rail-clamp the result, or feed the corrected lane back into that tick's already-completed `MoveState`. Include a post-longitudinal witness and a chained three-runner overlap witness.

6. **Whole-batch terminal freeze is an explicit wrapper policy.** The retail loop continues post-goal runners and has dedicated finished-runner minimum, deceleration, and movement branches; `step_forward_retail_with_roster` explicitly sets minimum 5 for a finished runner and skips its front-blocker minimum reduction (`race_solver_retail.rs:994-1027`), while `MoveState` receives `after_goal` and the speed update has a finished branch (`race_solver_retail.rs:1184-1187,1204-1217`). M3b integration instead inherits the accepted M3a first-finish/all-timeout batch truncation. Complete the whole crossing passâ€”including later-index runners and overlapâ€”then freeze every state leaf on later calls. Reject or clearly constrain inputs containing a finished runner in an otherwise active batch; do not imply that this wrapper policy is retail post-goal parity.

## Core-step snapshot review (2026-11-17)

Reviewed `globalsim_jax/moving_field.py` only against the integration schedule and previously accepted primitives. No tests were run because the implementation is still being edited; no implementation files were changed.

The core carries tick-entry positions/lanes into side queries and ranks/front IDs/gaps from `prepare_blocking` (`moving_field.py:34-44`); each runner's lateral movement uses those cached values (`47-54`). Its indexed loop publishes each updated runner into `runners` before later iterations, so blocker speed is live in runner order (`49-58`). `active` prevents lane carry updates on closed gates, terminal/finalized runners, and rows already at distance (`54-55`); the restricted longitudinal step independently applies gate fraction to distance. `move_step`'s returned state is retained for active runners even when `did` is false, which preserves the source blocked-move momentum/target/direction state. Overlap runs once after the loop on final positions and lanes (`59-64`). The final `old.truncated` mask freezes all pytree leaves only for batches terminal before this call, while a newly crossing batch completes its pass (`62-68`). These are correct snapshot-level observations; independent traces are still required.

**Re-evaluation â€” the minimum prepass is source-order equivalent (false positive resolved).** The earlier note treated `prepared.minimum` as if every runner's new value were computed independently or visible to every owner. The actual dataflow is sequential: `prepare_blocking` starts its `fori_loop` from `state.minimum` (the previously stored values) at `field.py:146`; at index `i`, it reads the current carry's blocker value (`141`) and writes only owner `i`'s recalculated value (`142-144`). Thus a blocker with index `j > i` is still represented by its prior stored minimum when owner `i` is processed, while a blocker with `j < i` already has its newly calculated value, exactly matching Rust's ordered lookup. `moving_field.step` then uses only the owner's computed `prepared.minimum[:, index]` for that runner's cap and longitudinal minimum override (`moving_field.py:50,57`); it does not re-read a blocker minimum during movement. The speed operand is separately gathered from the evolving runner carry (`49`), so earlier runners' speed changes remain live. In the restricted profile, no skills/callbacks mutate guts or other minimum inputs between preparations and movement. The prepass preserves the relevant source observation semantics; there is no demonstrated counterexample and no requirement to move minimum recomputation into the movement loop.

**Disposition:** the reported minimum-order discrepancy is withdrawn as a false positive. The core-step snapshot has no actionable defect identified in this finite static review. Final implementation acceptance still requires the independent Rust ordered moving-field fixture and eager/JIT/batch/full-state assertions listed above; this snapshot itself does not claim those tests or oracle evidence.
